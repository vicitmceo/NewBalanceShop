# Імовірні запитання викладача і чесні короткі відповіді

1. **Навіщо Clean Architecture, а не один проєкт?**
   Чотири проєкти: Domain без залежностей, Application залежить від Domain, Infrastructure (EF Core, репозиторії, перевірка Google-токена) залежить від Application, Web API збирає все через DI. Бізнес-логіка не знає про БД і Firebase, тому її легко тестувати моками. Firebase спочатку лежав в Application, ми винесли його за інтерфейс.

2. **Що таке BOLA і як ви її закрили?**
   Broken Object Level Authorization: покупець міг підставити чужий customerId і побачити чужі замовлення. Тепер customerId береться лише із серверної сесії в `/api/Orders` і checkout, чужі замовлення дають 403/404. Це покрито інтеграційними тестами.

3. **Як зберігаються паролі?**
   PBKDF2-HMAC-SHA256, 100 000 ітерацій, сіль 16 байт, хеш 32 байти, порівняння через FixedTimeEquals. Формат «ітерації.сіль.хеш». Для Google-користувачів пароль не зберігається. Пароль адміна в репозиторії лише як хеш.

4. **Чому сесії в пам'яті, це ж погано?**
   Так, це відома межа. Сесії живуть у пам'яті процесу: після перезапуску сервера користувачів розлогінює, а на кількох інстансах не працюватиме. План: Redis або таблиця в БД. Для навчального проєкту на одному безкоштовному інстансі це свідомий компроміс.

5. **Скільки тестів і що вони дали?**
   295 тестів: 190 unit і 105 integration, усі зелені, покриття рядків 93,4%. Інтеграційні йдуть через повний HTTP-конвеєр на EF InMemory. Тести знайшли реальні баги: Forbid давав 500 замість 403, Secure-cookie ламала сесію, конфлікт двох провайдерів БД.

6. **Чи є CI?**
   Так, GitHub Actions (`ci.yml`) в обох репозиторіях. Бекенд: restore, build, тести з покриттям. Фронтенд: lint і build. Обидва зелені. Окремого автодеплою немає: Render і Vercel самі збирають при push.

7. **Що показав ZAP?**
   OWASP ZAP baseline по фронтенду: 0 High, 4 Medium, 4 Low, здебільшого відсутні заголовки (CSP, anti-clickjacking, nosniff, Permissions-Policy). Ці заголовки додано в `vercel.json`, на живому сайті вони є. Повторний повний скан після виправлень не проганяли; відкритими лишаються SRI та COOP/COEP.

8. **Як організовано Scrum?**
   Jira, 8 спринтів по одному тижню (не по два), спринти 1-7 закрито, 8 активний. 44 задачі, 33 виконано. Чесно: деякі статуси в Jira відстають від коду, наприклад CI вже зроблено, а картка ще відкрита.

9. **Чому в Git майже всі коміти від одного автора?**
   Усі 114 комітів (бекенд 71, фронтенд 43) написав Рафаїл. Внесок Team Lead (Панчук Вадим) у Git нульовий; його роль планування, Jira, документи. Це чесно зазначено на слайді, коміти внесок не вимірюють.

10. **Що буде з БД після листопада?**
    Безкоштовна PostgreSQL на Render діє до ~18.11.2026 і потім видаляється. Міграція запланована: перенесення на інший безкоштовний хостинг PostgreSQL через дамп і відновлення, зміна `DATABASE_URL`. До захисту це не критично, але на довгий строк потрібно зробити.

11. **Звідки фото й назви товарів, чи це законно?**
    Фото й назви з newbalance.com для навчального макета. Магазин не афілійований з брендом, на сайті це написано в підвалі. Для реального продажу потрібні ліцензії або власні фото. Раніше ми використовували вільні фото з Wikimedia та типографські плитки.

12. **Чому немає оплати?**
    Це навчальний макет: оформлення замовлення створює замовлення зі статусом New, оплати немає. Інтеграція з платіжним провайдером потребує договорів і PCI-вимог, виходить за межі курсу. У монетизації вказано як наступний крок.

13. **Чому запити /api йдуть через домен сайту?**
    Сайт на Vercel, API на Render: різні домени, а браузери блокують «сторонні» куки. Vercel проксує `/api` на сервер, тож кука належить домену сайту, і сесія працює без SameSite=None.

14. **Як захищено адмін-функції?**
    Атрибут RequireAdmin на сервері: без входу 401, звичайний покупець 403. Запис товарів, блокування й видалення користувачів, зміна статусів замовлень доступні лише адміну. Приховування кнопок на фронтенді не вважаємо захистом.

15. **Як працюють фільтри каталогу?**
    Параметри в адресі (`g`, `cat`, `type`, `size`, `min`, `max`, `sort`, `sale`), фронтенд передає їх у `/api/Products`, фільтрує сервер (`gender`, `type`, `sale`, `sort=new`). Список категорій `GET /api/Categories` кешується.

16. **Які обмеження вашого рішення?**
    БД до ~18.11.2026; сесії в пам'яті процесу; безкоштовний Render засинає, перший запит повільний; фото з newbalance.com; немає оплати; на вузькому екрані 390 px сітка каталогу має зсув правої колонки; частина заголовків безпеки (SRI, COOP/COEP) не додана.

17. **Чому два способи входу, а не три?**
    GitHub-вхід прибрали: він давав зайву складність (окремий OAuth-потік) без користі для покупців магазину. Лишилися пароль і Google.

18. **Що б зробили далі?**
    Redis для сесій, перенесення БД, оплата, повторний скан ZAP, виправлення сітки на мобільному, автодеплой із CI.
