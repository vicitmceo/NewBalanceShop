## 1. Вступ

### 1.1. Мета документа

Цей документ визначає повний набір функціональних та нефункціональних вимог до веб-платформи **New Balance Shop** — інтернет-магазину спортивного одягу та взуття, що розробляється в рамках курсового командного проєкту з дисципліни ASP.NET Core. Документ є єдиним джерелом правди для команди розробки та викладача на всіх етапах: планування, реалізація, тестування, захист.

### 1.2. Область застосування продукту

New Balance Shop — сучасна веб-платформа електронної комерції, що дозволяє користувачам переглядати каталог товарів (кросівки, одяг, аксесуари), фільтрувати за категорією/розміром/ціною, додавати товари в кошик, оформлювати замовлення та переглядати історію своїх покупок. Адміністратор керує каталогом товарів через окремі CRUD-ендпоінти.

## 2. Загальний опис

### 2.1. Перспектива продукту

New Balance Shop розробляється як самостійний веб-застосунок електронної комерції з нуля. Продукт вирішує задачу курсового проєкту — побудову багатошарового ASP.NET Core застосунку (Clean Architecture) з повним циклом CRUD-операцій над товарами, кошиком і замовленнями. Система складається з серверного Web API (ASP.NET Core) та бази даних (SQL Server), з можливістю подальшого підключення окремого frontend (React або аналогічний SPA) у наступних ітераціях.

### 2.2. Класи користувачів і привілеї

| Роль | Опис | Ключові дозволи |
|---|---|---|
| Гість | Неавторизований відвідувач | Перегляд каталогу, фільтрація, покупка товару **без обов'язкової реєстрації** (за методичкою курсу — реєстрація не є обов'язковою умовою покупки) |
| Покупець | Зареєстрований користувач | Кошик, оформлення замовлення, кабінет із особистими даними (ПІБ, місто, країна, телефон, email), історія замовлень (тільки перегляд, без редагування) |
| Адміністратор | Керівник магазину | CRUD товарів і категорій (з підтвердженням при видаленні), перегляд усіх замовлень, зміна статусу замовлення, перегляд/блокування/видалення користувачів |

## 3. Границі проєкту

### 3.1. В рамках проєкту (In Scope)

- Каталог товарів (кросівки, одяг, аксесуари) з категоріями, розміром, кольором, ціною, залишком на складі
- CRUD-операції над товарами (Create/Read/Update/Delete) через REST API
- Фільтрація товарів за категорією
- Модель кошика та замовлення (Domain-рівень) з позиціями замовлення
- Clean Architecture: чіткий поділ на Presentation / Application / Domain / Infrastructure
- Repository pattern + Service-шар для бізнес-логіки
- Документація API (Swagger/OpenAPI)

### 3.2. Поза рамками проєкту (Out of Scope, поточна ітерація)

- Повноцінна реєстрація/авторизація користувачів (буде додано в наступній ітерації)
- Онлайн-оплата (інтеграція з платіжними системами)
- Frontend SPA (React) — окрема ітерація курсу
- Рекомендаційна система товарів

## 4. Функціональні вимоги

Формат: `[Пріоритет MoSCoW] ID — Опис → Критерій прийняття (AC)`

### 4.1. Каталог товарів

- **[Must] FR-01** — Перегляд списку всіх товарів. → AC: `GET /api/products` повертає JSON-масив товарів.
- **[Must] FR-02** — Перегляд одного товару за id. → AC: `GET /api/products/{id}` повертає товар або 404, якщо не знайдено.
- **[Should] FR-03** — Фільтрація/пошук товарів за назвою, брендом, ціною, категорією, розміром, кольором. → AC: `GET /api/products?categoryId=&size=&color=&minPrice=&maxPrice=` повертає лише товари, що відповідають заданим параметрам.
- **[Must] FR-04** — Створення нового товару (адміністратор). → AC: `POST /api/products` з валідними даними створює запис і повертає 201 з посиланням на ресурс.
- **[Must] FR-05** — Оновлення товару та категорій. → AC: `PUT /api/products/{id}` оновлює запис, повертає 204; 404, якщо товару не існує; аналогічно для `PUT /api/categories/{id}`.
- **[Must] FR-06** — Видалення товару з підтвердженням. → AC: `DELETE /api/products/{id}` видаляє запис лише після явного підтвердження на клієнті, повертає 204; 404, якщо товару не існує.

### 4.2. Кошик і замовлення

- **[Must] FR-07** — Кошик замовлення (обов'язково за темою проєкту): додавання/видалення позицій, підрахунок суми. → AC: сутність `Order` пов'язана з `OrderItem` через зовнішній ключ, `TotalPrice` рахується як сума `Quantity * Price`.
- **[Must] FR-08** — Оформлення замовлення з кошика без обов'язкової реєстрації. → AC: `POST /api/orders` приймає дані покупця (ПІБ, контактний телефон, e-mail) навіть без автентифікації.
- **[Could] FR-09** — Статус замовлення (New/Confirmed/Shipped/Delivered/Cancelled). → AC: поле `Status` в `Order` має тип enum, адміністратор може його змінювати.

### 4.3. Кабінет покупця

- **[Must] FR-10** — Перегляд і редагування особистих даних (ПІБ, місто, країна, контактний телефон, e-mail). → AC: `PUT /api/customers/{id}` оновлює всі поля, крім історії замовлень.
- **[Must] FR-11** — Перегляд історії власних замовлень (тільки читання). → AC: `GET /api/customers/{id}/orders` повертає список замовлень покупця; редагування історії заборонено на рівні API.

### 4.4. Адміністрування користувачів

- **[Must] FR-12** — Перегляд списку зареєстрованих користувачів. → AC: `GET /api/customers` доступний лише ролі Адміністратор.
- **[Must] FR-13** — Блокування або видалення користувача. → AC: `PATCH /api/customers/{id}/block` і `DELETE /api/customers/{id}` доступні лише ролі Адміністратор.

## 5. Use Cases

### UC-01: Перегляд каталогу товарів

| | |
|---|---|
| Актор | Гість / Покупець |
| Передумови | Застосунок запущено, БД доступна |
| Основний потік | 1. Клієнт надсилає `GET /api/products` → 2. API повертає список товарів → 3. Клієнт відображає картки товарів |
| Альтернативний потік | 2a. Товарів немає → API повертає порожній масив |
| Постумови | Список товарів відображено |

### UC-02: Адміністратор додає новий товар

| | |
|---|---|
| Актор | Адміністратор |
| Передумови | Адміністратор має доступ до API |
| Основний потік | 1. Адміністратор надсилає `POST /api/products` з даними товару → 2. Сервіс валідує дані (data annotations) → 3. Репозиторій зберігає товар у БД → 4. API повертає створений товар з `Id` |
| Альтернативний потік | 2a. Дані невалідні → API повертає 400 з описом помилок |
| Постумови | Новий товар з'являється в каталозі |

### UC-03: Оформлення замовлення (заплановано, Domain готовий)

| | |
|---|---|
| Актор | Покупець |
| Передумови | Покупець обрав товари в кошик |
| Основний потік | 1. Покупець підтверджує кошик → 2. Система створює `Order` зі списком `OrderItem` → 3. Розраховується `TotalPrice` → 4. Замовлення отримує статус `New` |
| Постумови | Замовлення збережено, доступне в історії покупця |

## 6.4. Технологічний стек курсового проєкту (вимога методички)

| Технологія | Статус | Де застосовується |
|---|---|---|
| Repository pattern | ✅ Реалізовано | `Infrastructure/Repositories/*` |
| SOLID / Clean Architecture | ✅ Реалізовано | розподіл на 4 шари |
| LINQ / Fluent API | ✅ Реалізовано | `ShopDbContext` конфігурація моделей, запити репозиторіїв |
| EF Core + SQL Server | ✅ Реалізовано | `Infrastructure/Data/ShopDbContext.cs` |
| Async/await | ✅ Реалізовано | усі методи репозиторіїв/сервісів асинхронні |
| Unit of Work | 🔲 Заплановано | обгортка над `SaveChangesAsync` при рості кількості репозиторіїв |
| Аутентифікація та авторизація | 🔲 Заплановано | ASP.NET Core Identity або JWT для ролей Покупець/Адміністратор |
| Кешування | 🔲 Заплановано | `IMemoryCache` для списку категорій/популярних товарів |
| Логування | 🔲 Заплановано | вбудований `ILogger` + middleware обробки помилок |
| Тестування (NUnit) | 🔲 Заплановано | `ProductService`, `OrderService` |
| Документація (OpenAPI/Swagger) | 🔲 Заплановано | генерація HTML-сторінок специфікації API |
| SignalR / мікросервіси | 🔲 Не пріоритетно | розглядається для сповіщень про статус замовлення, якщо дозволить час |
